# Havemind MVP specification

- Status: **Approved by owner on 2026-07-15**
- Date: 2026-07-15
- Working plugin ID: `havemind-sync`
- Working product name: `Havemind`

> Network, identity and onboarding assumptions that require Tailscale are superseded by the approved `002-public-access.md` amendment. The open-source publication path is defined by the approved `003-open-source-release.md` amendment.

## 1. Goal

Two trusted people work in separate, ordinary local Obsidian vaults. Havemind synchronizes their notes through `sapserver` and shows a durable record such as:

> Anna changed `Projects/Plan.md` at 14:32 (+8, -2).

Both people can work offline. When a device reconnects, its queued changes are uploaded and remote changes are applied. Concurrent work must never silently delete either person's content.

## 2. Approved assumptions, as amended

1. The first release records authorship per saved revision and maintains provenance for visible text fragments. A toggle named `Show authors` colors fragments by the person who last introduced or changed them.
2. The first release is near-real-time synchronization after save, not two live cursors typing in the same paragraph.
3. The private pilot may use Tailscale as transport, but Havemind membership and actor identity come from the built-in device session described in `002-public-access.md`.
4. Development starts with two disposable test vaults. A real private vault is not connected until conflict and restore tests pass.
5. Phase 1 supports Markdown files. Attachments are added and tested before declaring the system ready for a complete real-world vault.
6. Obsidian must be open for synchronization. Mobile operating systems may pause the plugin in the background.
7. A color means "last changed by this person in Havemind history", not legal or forensic proof of the original author. Content that predates Havemind is labeled as an initial import.

## 3. User experience

### Owner setup

1. Install the Havemind plugin and open a disposable test vault.
2. Select `Create a shared vault` in the connection wizard.
3. The wizard verifies HTTPS, server discovery, protocol compatibility and the current Havemind device session.
4. Create the remote vault and perform the initial upload.
5. Enter the collaborator's display name and select `Create invitation`.
6. Send the generated one-time HTTPS invitation link.

### Collaborator setup

1. Create an empty local Obsidian vault and install Havemind.
2. Open the invitation landing page, copy its secure envelope, and open the Havemind wizard in Obsidian.
3. Paste the envelope once. Obsidian shows the verified server host, shared-vault name and inviter.
4. Confirm the connection and compare the human-readable device phrase with the owner.
5. After owner approval, download the initial state automatically.

Havemind must not automatically merge two pre-existing vaults during onboarding.

### Daily use

- Both collaborators can normally create, edit, rename, move and delete shared notes.
- Local edits save normally and are queued automatically.
- New remote revisions appear within ten seconds while both apps are online.
- A notice identifies the other person and changed note.
- An Activity view lists create, edit, rename, delete and conflict-resolution events.
- Selecting an event opens its line diff and allows restoring that revision.
- A toolbar/ribbon button and command-palette action toggle `Show authors` on and off.
- With the overlay enabled, each author's fragments use a consistent accessible color and a non-color marker. Hovering or focusing a fragment shows the name and revision time.
- A small legend identifies the two people and the `Initial import` state.
- A status item shows `Synced`, `Syncing`, `Offline`, or `Conflict`.

### Authorship overlay behavior

- The overlay is off by default and its state is remembered per local vault.
- In Source and Live Preview modes, CodeMirror decorations mark exact text ranges without modifying Markdown content.
- In Reading view, the first release shows block-level author markers where exact source-to-DOM mapping is ambiguous. Exact rendered-fragment highlighting can follow after the editor implementation is proven.
- Colors never enter frontmatter or the note body.
- The two default colors must remain distinguishable in light and dark themes. Labels, underline styles and tooltips ensure that color is not the only signal.
- Clicking an attributed fragment opens the revision in the Activity view.
- Existing imported content is marked `Initial import`, unless its earlier Havemind history is available.

## 4. Scope

### Included in the MVP

- two users and multiple devices;
- local/offline editing;
- create, update, rename and delete for `.md` files;
- append-only revision history;
- server-authenticated actor identity;
- activity feed, notices and per-revision diff;
- toggleable text-provenance overlay;
- one-time invitation link and guided connection wizard;
- idempotent retry after network or process failure;
- explicit conflict handling without silent overwrites;
- initial import into an empty second vault;
- versioned HTTPS access independent of ingress; the private pilot may use Tailscale Serve;
- Docker Compose deployment on `sapserver`;
- backup and documented restore procedure.

### Required before using a complete real vault

- binary attachments as atomic versions;
- storage quota and retention policy;
- successful backup-restore drill;
- successful two-device destructive test matrix;
- a documented decision on client-side end-to-end encryption.

### Not included initially

- live cursors or per-keystroke co-editing;
- proof of authorship for content created before Havemind was installed;
- exact character-level highlighting in rendered Reading view during the first vertical slice;
- public Internet access or Tailscale Funnel;
- syncing `.obsidian/**` settings and community plugins;
- automatic merging of two existing vaults;
- public Community Plugin publication;
- background sync while Obsidian is closed.

## 5. Architecture

```text
Obsidian A + Havemind plugin
          |
          | HTTPS over Tailscale Serve
          v
127.0.0.1:8787 -> Havemind server -> SQLite + revision blobs
          ^
          | HTTPS over Tailscale Serve
          |
Obsidian B + Havemind plugin
```

### Repository layout

```text
havemind/
├── manifest.json
├── versions.json
├── src/                    # Obsidian plugin
├── apps/server/            # Private sync API
├── packages/protocol/      # Shared schemas
├── packages/sync-core/     # Platform-neutral sync logic
├── infra/compose.yaml
├── specs/
└── docs/
```

### Client

- TypeScript and the official Obsidian API.
- `Vault` events for create, modify, rename and delete, registered after layout readiness.
- Platform-neutral queue and merge logic kept outside the Obsidian adapter.
- IndexedDB for pending operations, known revisions and the server cursor.
- `requestUrl()` for HTTPS push/pull without CORS problems.
- `registerEditorExtension()` with CodeMirror 6 decorations for the author overlay.
- `registerMarkdownPostProcessor()` for Reading-view block markers.
- A ribbon action and command named `Show authors`.
- `registerObsidianProtocolHandler("havemind-join", ...)` to open the reviewed invitation wizard without carrying a secret in the query.
- `Vault.process()` for safe background-file updates.
- An active note is never blindly overwritten; it is deferred or updated through the editor-aware path.
- No Node.js or Electron-only APIs, so the design remains mobile-compatible.

### Server

- Node.js 22, TypeScript and Fastify.
- SQLite in WAL mode for one small server instance.
- Revision payloads stored in a protected application-data volume.
- REST batch push/pull; polling on startup, focus, reconnect and every five seconds.
- Optional WebSocket wake-up signal only after the REST protocol is proven.
- Docker publishes the container only as `127.0.0.1:8787` on the host. The container listener is confined to its private Docker network and has no LAN or public host binding.

### Identity and authorization

- Havemind authenticates its own members and devices independently of Tailscale or another ingress.
- Every shared vault has an explicit allowlist and roles: `owner` or `editor`.
- Both `owner` and `editor` can create, edit, rename, move, delete and restore shared content. The `owner` additionally manages invitations and membership. Permanent history compaction is deferred until encrypted checkpoints are designed.
- The server derives `actor_id` from the authenticated request. It ignores any client-supplied author field.
- Proxy identity headers are not a trusted source of product identity.
- An invitation is a 256-bit opaque random token, stored only as a hash on the server, bound to one vault, single-use and valid for 15 minutes.
- Redeeming an invitation creates a pending device. The owner confirms it after comparing a human-readable verification phrase.
- Short access credentials and rotating device-specific refresh credentials follow `002-public-access.md`.
- The HTTPS invitation fragment contains a versioned envelope with the server origin and invitation token. The `obsidian://` wizard-opening link contains no capability, and neither link contains a vault encryption key.
- Opening a link never joins silently: the plugin validates its shape, allowlists `https`, displays the normalized hostname and requires explicit confirmation.

## 6. Engineering contract

### Tech stack

- Obsidian plugin: TypeScript, official `obsidian` API, CodeMirror 6, esbuild and Vitest.
- Server: Node.js 22 LTS, TypeScript, Fastify and SQLite in WAL mode.
- Shared validation: Zod schemas in `packages/protocol`.
- Deployment: Docker Compose behind a supported HTTPS ingress; the private pilot uses Tailscale Serve.

### Commands

```bash
npm ci
npm run dev
npm run build
npm run lint
npm test -- --run
npm run test:integration
docker compose -f infra/compose.yaml config
docker compose -f infra/compose.yaml up -d
```

### Code style

- English identifiers, comments and commit messages.
- Small pure functions in `sync-core`; Obsidian and Fastify adapters stay thin.
- Validate all external data at the boundary and use explicit result types for expected conflicts.

```ts
export function applyRemoteRevision(
  state: FileState,
  revision: RemoteRevision,
): ApplyResult {
  const validatedRevision = remoteRevisionSchema.parse(revision);
  return mergeRevision(state, validatedRevision);
}
```

### Boundaries

- **Always:** validate inputs, preserve every conflicting head, write tests before behavior, run build/lint/tests, and redact invitations and note content from logs.
- **Ask first:** change the revision schema after real data exists, add a network-facing dependency, expose a port, enable public access, or migrate a real vault.
- **Never:** trust a client-supplied author, put an encryption key in an invitation URL, modify note text to render attribution, silently discard a revision, commit secrets, or enable Tailscale Funnel.

## 7. Revision and provenance model

Each logical file has a stable random `file_id` independent of its path. A revision is split into a routable protected header, a content-sensitive payload and a server receipt:

```text
client_protected_header:
  revision_id
  vault_id
  file_id
  parent_revision_ids[]
  payload_format_version
  sync_semantics_version
  provenance_recipe_version
  path_normalization_version
  payload_encoding
  expected_member_id
  expected_device_id

opaque_payload:
  operation: create | update | rename | delete | restore | resolve
  path and previous path
  full normalized content or tombstone
  plaintext_content_hash
  reconstruction recipe

server_receipt:
  actor_id
  device_id
  server_sequence
  server_time
  blob_hash
```

Rules:

- `revision_id` makes byte-identical retries idempotent.
- `server_sequence` is the pull cursor, not the causal history.
- `parent_revision_ids` describe causality and expose concurrent heads.
- A rename keeps the same `file_id` so history is not lost.
- A delete creates a tombstone and is reversible while its history is retained.
- The full version is the source of truth in the MVP; a diff alone is never the only stored copy.
- The server checks expected member/device IDs against the authenticated session and assigns the authoritative receipt identity.
- The server treats the payload as opaque so the same revision envelope can carry authenticated ciphertext after E2EE is enabled.
- A provenance run stores a text range, the revision that introduced or last changed it, and that revision's server-authenticated actor.
- Unchanged text retains its previous provenance. Inserted or replaced text receives the current revision's actor. Deleted text remains visible only in history.
- Every receiving client derives provenance from authenticated revision receipts plus a validated reconstruction recipe; invalid payloads are quarantined rather than applied.
- Attribution is a deterministic collaboration history, not forensic proof against a malicious collaborator or server administrator.
- Initial-upload ranges use the special `initial_import` source instead of claiming that the uploader originally wrote them.

## 8. Conflict policy

No incoming revision may silently overwrite a different concurrent revision.

- Different files: apply independently.
- Same Markdown file, non-overlapping edits: perform a three-way merge against the common parent.
- Same lines changed: keep both heads, create a visible conflict copy and show a resolution screen.
- Edit versus delete: retain the edited content and require an explicit decision.
- Rename versus edit: the edit follows `file_id` to the renamed path.
- Rename versus rename: retain both proposed names and require a decision.
- Conflicting binary files in the attachment phase: keep both versions under distinct names.
- Applying a remote write uses an echo-suppression marker plus an expected hash so it is not uploaded as a new local edit.
- Automatic merges preserve provenance from both source revisions. Text manually added during resolution belongs to the resolver's new revision.

Unresolved conflicts must also be represented in a visible `Havemind Conflicts/` folder, not only hidden in plugin storage.

### Deletion behavior

- Deleting a note is a normal action available to both collaborators and is synchronized to every connected vault.
- Remote deletion uses the local Obsidian trash behavior instead of an irreversible filesystem removal where the platform supports it.
- The client interprets the opaque revision as a tombstone and records a local Activity event such as `Anna deleted Projects/Plan.md` using the authenticated server receipt.
- Either collaborator can restore the note together with its path, content and attribution history by creating a new revision from the historical payload.
- The disposable pilot retains all revision payloads. Permanent purge/compaction is deferred until encrypted provenance checkpoints and safe new-device bootstrap are specified.
- A delete concurrent with an edit never destroys the edited version; Havemind asks whether to restore the edit or keep the deletion.

## 9. Security and privacy

### Pilot protection

- private tailnet access only;
- HTTPS through Tailscale Serve, never Funnel;
- explicit two-user allowlist;
- backend on localhost only;
- non-root container, read-only root filesystem where practical;
- `cap_drop: ALL`, `no-new-privileges`, resource limits and health check;
- data under `/srv/appdata/havemind` and configuration under `/srv/secrets/havemind`;
- path normalization, vault-root containment and file-size limits;
- rate limits and bounded request bodies;
- no client analytics or unrelated telemetry;
- activity records are a product feature and documented as personal data.
- invitation values are redacted from client and server logs, expire after 15 minutes and are invalidated atomically after use;
- the join screen rejects non-HTTPS servers, unexpected URL fields, oversized values and identity mismatches.

### Explicit limitation

The pilot server can read stored note content. Tailscale protects transport and access but does not make the server zero-knowledge. Therefore the pilot uses disposable data only.

Before a sensitive real vault is approved, implement client-side end-to-end encryption of revision payloads and attachments with a vault key, device approval and a tested recovery kit. The server must not hold the decryption key.

No home-grown cipher will be used.

## 10. Backup and recovery

- Daily consistent SQLite backup using its backup mechanism, not a raw WAL copy.
- Backup of revision payloads in the same logical snapshot window.
- Encrypted Restic repository on a second physical disk or external storage.
- Retain daily, weekly and monthly generations within the server's 120 GB constraint.
- Document recovery of a new empty server and a new empty client.
- Synchronization is not treated as backup because it propagates deletion and corruption.

## 11. Test strategy

Implementation follows red-green-refactor for the protocol and sync core.

### Unit tests

- operation validation and canonical hashing;
- idempotency and server cursor ordering;
- stable file IDs across rename;
- echo-loop suppression;
- three-way merge and conflict creation;
- Unicode and path normalization;
- authorization and spoofed-header rejection at the direct backend boundary;
- deletion, reversible tombstones and deferred compaction safety;
- deterministic provenance updates for insert, replace, delete and merge;
- overlay ranges after Unicode, Markdown syntax and multiline changes;
- invitation parsing, expiry, single use and exact identity binding.

### Integration tests

- two simulated clients exchanging create/update/rename/delete;
- offline queues delivered out of order and more than once;
- restart during upload and during local apply;
- concurrent non-overlapping and overlapping edits;
- edit/delete and rename/edit races;
- an unauthenticated or cross-vault device gets `401`/`403` without data disclosure;
- a stolen invitation cannot become an approved device without owner confirmation;
- a redeemed or expired invitation cannot be reused;
- server unavailable and later recovered;
- database and blob restore into a clean instance.

### Manual acceptance tests

- two disposable Obsidian vaults on two computers;
- create on A appears on B with A's identity within ten seconds;
- edit on B appears on A with B's identity and the correct diff;
- toggling `Show authors` changes only editor decorations and never the Markdown file hash;
- attributed ranges retain consistent identities after restart and non-overlapping merge;
- an invitation deep link shows a confirmation screen and connects the invited identity to an empty vault;
- either collaborator can delete a note, the other vault removes it, Activity identifies the deleter, and restore reconstructs the note;
- simultaneous same-line edits preserve both texts and display a conflict;
- an offline device reconnects without duplication or loss;
- service survives Obsidian, Docker and server restarts;
- no API port is reachable directly from LAN or the public Internet;
- restored backup reconstructs the shared test vault and activity history.

## 12. Delivery phases

1. **Protocol test harness** — two in-memory clients, revision DAG and conflicts.
2. **Server vertical slice** — identity, SQLite, push/pull and Docker tests.
3. **Connection vertical slice** — built-in device identity, one-time invitation, verification phrase and reviewed deep link.
4. **Plugin vertical slice** — two test vaults synchronizing Markdown.
5. **Attribution UX** — activity view, notices, diff, restore and author overlay.
6. **Hardening** — fault injection, limits, backups and security review.
7. **Attachment support** — atomic binary versions and quotas.
8. **Real-vault safety** — client-side E2EE, recovery, attachment and backup/restore gates.
9. **Optional CRDT phase** — Yjs/live cursors only if real usage proves it necessary.

## 13. Approved delivery decisions

The owner approved this specification with the following delivery decisions:

- the overlay means "who last changed this visible fragment", while imported text is labeled `Initial import`;
- exact highlighting is required in Source/Live Preview first, with block-level markers in Reading view initially;
- live simultaneous cursors can wait;
- both people will use separate Tailscale identities;
- connection through a reviewed, single-use invitation link is the desired onboarding flow;
- Markdown-first development on disposable vaults is acceptable;
- desktop macOS and Windows/Linux are the first acceptance targets; the code remains mobile-compatible, but mobile acceptance does not block the pilot;
- client-side encryption is mandatory before any real private notes are uploaded.
