Havemind — one hexagon, one pane

Every state below is one Obsidian right-hand pane drawn at 300px (one is drawn at 258px to prove the floor). Colours are Obsidian's own semantic variables, set as real CSS custom properties on each pane so the same markup renders in light and dark — see 1g. Author colours come straight from author-palette.css.

My answers to your five

  1. Neither tabs nor a stack — a priority column. Tabs put a conflict behind a click and force you to invent a badge to undo the hiding you just did; five labels at 300px truncate to noise. So: one scrolling column where status is always drawn, anything actionable injects itself directly under status, and everything idle collapses to a single summary row. The pane's length becomes a readout of how much is wrong. See 1a; 1c is the tab version, built so you can see why not.
  2. Nearly empty — with one amendment. I agree with your position and I'd push on one point: empty and alive are different. A pane showing only "Synced" is indistinguishable from a pane that stopped updating three days ago. So the calm state keeps one proof-of-life line ("Last change 4 min ago") and two summary rows that carry counts. Four lines total, no headings, no colour. 1b is the alternative if you'd rather the feed always be open.
  3. Urgency = the only filled surface in the pane. The calm pane has no fill anywhere: hairlines, muted text, one 8px dot. So the first tinted block a user ever sees is the thing that needs them — no badge grammar to learn. Three tiers: status word changes (Conflict / Offline), a 2px rule + 7% wash block appears under it, and the ribbon hexagon takes a dot. Nothing animates, nothing is red-on-red. 1a, panes 3 and 4.
  4. Two stacked rows, invitation first, each naming the thing the user is holding. Not side-by-side cards — at 300px that's 140px a card and both titles wrap. The discriminator is a possession, not an intention: "someone sent you a long code" vs "you'll run Docker on a machine". Each row states its cost on the second line, so the wrong pick is visibly expensive before it's made, and both branches keep a back arrow. 1d.
  5. Make it a two-sided screen, not a display. The code is only meaningful because the other person is looking at the same six digits — so the guest pane says what to do with it in the imperative, and the owner's modal shows the digits it expects and asks "does the joining device show this?". Digits are 34px mono, grouped 3+3, with a live expiry. That's the whole screen; a cancel is the only other control. 1e.

What I would cut

  • The second ribbon icon. Authorship becomes a footer toggle in the pane plus its existing command.
  • All seven uppercase section captions. In a 300px column a caption costs a line and says what the row below already says.
  • The "Connection" block that echoes your own server URL. Nobody needs their own address daily — it moves to the header overflow menu with Disconnect and Reset.
  • The idle send-queue section. When it's empty it's not a section; when it's non-empty it's one clause on the status detail line, and only a failed send earns a block.
  • The waiting-devices section in the panel. A device only ever waits during an invitation, so it lives in the invitation modal where the owner already is.
  • The always-on five-step tutorial. It's correct for half your users and fatal for the other half — behind the chooser, then behind the life-buoy.
  • The status-bar text. "Havemind: Synced" duplicates the pane; the mark plus a state dot is enough, and it's the pane's job to use words.
  • "Reconnect required" and "Reset required" as their own sections. They're status words with one action attached, same as Offline.
  • Roster action rows in the calm state. Mark-offline / Remove / Rejoin live inside the expanded roster, not on first paint.

Assumptions I made

  • The pane never horizontally scrolls: paths ellipsise from the left (…/Kiln notes.md) so the filename always survives.
  • Restore is a real button in every activity row rather than a hover affordance — hover-only actions are unreachable by keyboard and invisible on first paint. Toggleable in Tweaks if you disagree.
  • Local vs remote is carried by the name ("You") and a hollow dot, so the author colour is never doing the work alone.
  • Every dot in this design has a title + aria-label naming the person or the state; every collapsed row is a button with aria-expanded.

Same information as 1a. Different chrome: an Obsidian nav-buttons-container under the header, and disclosure rows built as tree-item with a tree-item-flair count.

What changed and why. The single most repeated lesson from mature Obsidian plugins is: don't invent chrome — borrow Obsidian's. When the Obsidian Git author rebuilt his sidebar, he aligned it to Obsidian's own file view and reused their CSS classes, and the result reads as part of the app in every community theme.

So the footer rail from 1a becomes a toolbar under the header — the same row the File Explorer uses for "new note / new folder / sort". Users already know that row is where a pane's verbs live, and it puts the authorship toggle somewhere findable, which was the whole point of killing the second ribbon icon.

Rows become tree-item + tree-item-flair — Obsidian's own collapsible-list grammar, with the twisty on the left where the file explorer puts it, and the count in the flair slot where backlink counts live.

Cost: class names are undocumented and can shift between releases. Mitigation used by the good plugins: reuse the classes for layout and theming, but never depend on them for behaviour, and keep every Havemind-specific rule under .havemind-view as you already do.

Five findings, five decisions

1. One view type, revealed not re-created. Obsidian's own docs show the canonical pattern: look for an existing leaf of your view type, reuse it, and only then create one — then reveal it in case the sidebar is collapsed. That is exactly your AT0-2, and it is three lines of the documented example. Decision: one registered view, hexagon reveals it, commands focus the same leaf.

2. Tabs appear at two, not five. Sidebar plugins that do use tabs use exactly two peer lists (a Git sidebar plugin ships "Changes" and "History"). Nobody ships five in a 300px pane. Decision: no tabs. Two collapsible groups, everything urgent above them — 2a.

3. The two-path chooser is the established answer. Self-hosted LiveSync — the closest thing to a direct competitor — opens onboarding by asking whether this device owns the files or should receive an existing remote state, and only then shows the matching setup. Your joiner/host split is the same fork, phrased better. Decision: ship the chooser as designed in 1d.

4. The status bar is for the glance, the pane is for the words. LiveSync puts sync state in the status bar as icons and keeps the detail elsewhere. Decision: status bar = hexagon + state dot, no text; the pane owns every sentence. (Also: a plugin that never opens should still be reachable — keep a one-time persistent notice offering setup, the way LiveSync does, instead of hoping the user finds the ribbon.)

5. Register the hexagon as a real icon. Obsidian lets a plugin add a custom icon and then use it anywhere setIcon works. Decision: register the Havemind mark once and use it for the ribbon, the view icon (so the sidebar tab shows your mark, not a generic hexagon) and the status bar — one glyph, three places, no image files.

This pane says Synced while two files are in conflict one tab away. The dot is the only thing arguing otherwise — and it is 6px wide, on a truncated label, in a strip most people read once.

Five destinations do not fit: "Conflicts" truncates at 300px, the fifth tab overflows, and the state that matters is hidden behind a click by construction.

The structural objection. Tabs are for content of equal weight that the user chooses between. Here the weights are wildly unequal and change by the second — conflicts matter infinitely more than the roster, but only sometimes.

Once you add badges to fix that, you've rebuilt 1a badly: a summary of the thing, instead of the thing.
